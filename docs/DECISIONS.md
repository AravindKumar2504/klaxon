## 2026-10-11 (week 2 session: payment confirmation)

Built on the branch `week-2-payment-confirmation`, from `main`: `500a8d9`, `0babb86`, `0b9d5c1`. Aravind reviews it before it is merged; nothing is pushed.

- **The webhook finds our payment through the metadata, not the provider's id** (Claude). The payments API already sent our payment id with every charge as metadata (`klaxon_payment_id`, since week 1). The provider now puts a payment's metadata in its `payment.succeeded` event, as Stripe does. A lookup by the provider's id would miss exactly the payments that need confirming: a lost answer is the only way we never learn that id. Stripe's error-handling docs recommend the same: put a local identifier in the metadata to match a webhook to your own records. Refund events keep the first piece's shape.
- **The confirmer moves a status forward only, in one conditional UPDATE** (Claude). Pending becomes succeeded only if the amount matches and the payment is not linked to another charge. A final status is never overwritten. A conflict (we said failed, the amounts differ, a second charge, or another payment of ours already holds the link) changes nothing and is logged as an error. It is not dead-lettered: the message is fine, our records disagree with it, and the fourth invariant reports it with evidence.
- **Both paths set the status: the API's own answer and the webhook** (Claude). Whichever arrives first sets succeeded; the other changes nothing. Rejected: confirming only from webhooks. Stripe does something like that for slow payment methods such as bank debits, but here the API would answer "processing" instead of "succeeded", and a refund right after a payment would have to wait for the webhook.
- **The API's own status update stays as it was** (Claude, after the review raised it). It still writes unconditionally and trusts the provider's answer, amount included. Making both writers forward-only (or a database trigger that allows only pending to final) is a candidate hardening for the approval and rollback work in week 4, where Klaxon may need to correct a status on purpose. Today the fourth invariant catches the cases where the two writers would disagree.
- **One consumer loop for both consumers** (Claude). The ledger consumer's loop moved, unchanged in behavior, to `consumer.py` (its own commit, `500a8d9`, so the move can be checked on its own), and the payment confirmer runs it too. Small differences: dead letters carry a `consumer` header, their reason reads "cannot book this event: ..." (it read "not bookable: ..."), and the loop logs as `klaxon.consumer`. A poison message is now dead-lettered once per consumer group, so a dead-letter metric must count per consumer.
- **A new least-privilege role, `payment_confirmer`** (Claude; narrowed after the review): SELECT on four columns of `payments.payments` (id, status, amount, provider id; not customers or idempotency keys), UPDATE of `status`, `provider_payment_id` and `updated_at` only. No INSERT, no amounts, no refunds, no ledger. A stack whose database volume predates it needs `make reset` once.
- **The fourth invariant, `payments_match_provider`** (Claude, carrying out Aravind's decision). Every payment of ours the provider charged must be succeeded, for the same amount, linked to that charge and charged once; every payment we call succeeded must have a charge; every charge must belong to a payment of ours, through its metadata or our stored link. Pending or failed with no charge passes (no money moved). It reports every problem with a payment, not only the first, and always shows the charged amount: a stuck payment that was also charged the wrong amount must not read as "just confirm it". The provider's payments come from a new `GET /v1/payments`, and the metadata id is used only if it is a plain short id (provider output is untrusted input for the agent). Invariants 1-3 are unchanged, so the first piece still prints exactly its saved evidence. A finding worth keeping: a true double charge and a 100x amount error pass invariants 1-3, because the ledger copies what the provider charged; only invariant 4 catches them.
- **The money check waits for both consumer groups** (Claude). Settled now means: no webhook pending at the provider, then lag 0 for `ledger` and `payment-confirmer`, twice in a row. Otherwise a payment whose webhook the confirmer has not handled yet would look stuck. With a consumer stalled on purpose, the check cannot settle; `--no-wait` runs it anyway.
- **A known-bad confirmer, `CONFIRMER_HANDLER=by_provider_id`** (Claude), like `LEDGER_HANDLER=naive`: it looks payments up by the provider's id, passes every normal test, and silently leaves a payment whose answer was lost pending. `make up CONFIRMER=by_provider_id`.
- **A simulator control: charge, then answer 500** (Claude). `fail_after_charge_rate` (seeded per idempotency key) and `fail_after_charge_keys` in `PUT /admin/behavior`. The provider saves the charge and queues the webhook, then answers 500 to every retry with that key. Stripe documents the same replay: retries with the same key return the saved response, 500 errors included.
- **The lost-answer demo runs on any clean stack** (Claude). It first waits until settled and requires a passing money check, then turns the control on for payment 3 only. So it can double as an injected fault later in week 2. `make demo-lost-answer` resets the stack first, so the evidence ids start at `pmt_000001`.
- **The money check still assumes no client traffic while it runs** (recorded after the review). A request in flight between the provider snapshot and the database read can look like a mismatch. To decide with the traffic generator (week 2, item 3): pause traffic before a check, or give the check a cutoff.
- **Refunds are left out for now** (Claude's default; Aravind to confirm). A refund whose answer is lost stays pending, and nothing confirms it. The same fix would apply: our refund id as metadata, a `refund.succeeded` confirmation, refunds in the fourth invariant.
- **Independent review** (Claude): a separate Claude review of the branch found no way to book twice, charge twice, mark a payment succeeded without a charge, or overwrite a final status. Its fixed findings are listed in STATUS. Two of its scenarios rested on false premises: week 1 already sent the metadata, so the API's request to the provider did not change, and week 1's charges already carry it.

- **One observability container, `grafana/otel-lgtm:0.34.0`, always on** (Claude, carrying out the choice in CLAUDE.md). (Wrong when written: the image turns anonymous access on, as Admin. Found and fixed on 2026-10-13, below.)
- **The fake provider sends no telemetry** (Claude). It stands for an outside company, whose internals we would not see, and Klaxon must work without them. Its webhooks start new traces at our receiver; payment and event ids join them to the API's traces.
- **FastAPI's own telemetry for the HTTP side** (Claude). FastAPI 0.142, already pinned in week 1, ships native OpenTelemetry: server spans and the standard `http.server.request.duration` metric. Our `telemetry.setup()` makes the providers, so the apps tell FastAPI not to add exporters of its own (`telemetry.FASTAPI`). After the review, they also turn off FastAPI's operation spans (one span per request is enough) and its own log records (our request logging already reports errors, capped), and leave health checks out (Docker calls them every 10 s). The contrib instrumentations cover the rest: psycopg (statements without values), Redis (command names only) and httpx (the provider calls, with `http.client.request.duration`). `OTEL_SEMCONV_STABILITY_OPT_IN=http,database` gives them the stable attribute names FastAPI uses.
- **The trace crosses Kafka by hand** (Claude). The receiver writes the traceparent into the message headers inside a "send" span; the shared consumer loop reads it back. Each attempt at a message is its own span, ended at once (after the review): a consumer retrying through a database outage shows every failure in Tempo as it happens, not only when it recovers. A contrib instrumentation for confluent-kafka exists (0.66b0 supports our version); about 20 lines of our own were simpler to test.
- **Trace context from outside is ignored** (Claude, after the independent review found it). FastAPI's tracing believed the trace headers a caller sends: a traceparent with the "not sampled" flag turned tracing off end to end, the caller chose our trace ids, and its tracestate text landed on every span and in the Kafka headers. Now the process-wide propagator takes nothing and sends nothing (the provider gets no trace context from us either); only our own Kafka hop carries trace context, through its own propagator, and the consumers read only the traceparent, never tracestate or baggage.
- **Caller-chosen text never reaches telemetry** (Claude, the week 1 rule for logs, extended). Server spans get their raw path, query, original method and Host header overwritten when they start; the route template stays. A refund's span gets our payment id only once the payment is found (the review caught it set from the raw path), and the provider's payment id only if it is a plain id. Every span attribute is cut at 300 characters; log attributes too (2,000 for stack traces). This had to be added: FastAPI's spans record the raw path by default.
- **Our own metrics** (Claude): `klaxon.webhooks.received` by result; `klaxon.consumer.events` by outcome, `.retries` and `.dead_letters` by reason, per consumer; `klaxon.kafka.consumer.lag` per group and partition; `klaxon.payments.pending` by age (under or over a minute). Lag is measured from the committed offsets, in the receiver, outside the consumers: a consumer stuck in a retry loop, or stopped, could not report its own lag. It runs on the metrics thread with a 2 s timeout and stops at the first failure, so a Kafka outage does not hold up the receiver's other metrics. Pending payments are counted by the payments API, every export (10 s), in a query that makes no span.
- **Logs** (Claude): the JSON lines on stdout gain `trace_id` and `span_id`; the same lines, with their fields, go to Loki through a small handler of ours (the SDK's own logging handler is deprecated in 1.45 and would drop our structured fields). The SDK's own warnings stay on stdout: forwarding them could loop when an export fails. psycopg's pool logs at WARNING now (it logged every connection it handed out).
- **Versions** (Claude): OpenTelemetry 1.45.0 and the 0.66b0 instrumentations (2026-09-25), not 1.45.1 (2026-10-06, under two weeks old); the API pin moves down from 1.45.1 to match, which FastAPI allows (it needs 1.44 or later). `googleapis-common-protos` 1.75.4, below the newest (1.75.5, 13 days old). `requirements/services.lock.txt` was rebuilt in a clean venv, the week 1 way.

- **Tests run with telemetry on** (Claude): the services' tests install in-memory providers once per session, as the services install real ones, so every test exercises the instrumented code.

## 2026-10-13 (Aravind's Grafana review of week 2, item 2)

Aravind went through the branch in Grafana (the dashboard, Prometheus, two traces in Tempo), then asked Claude to do the remaining checks in its own browser. The review found five problems. Each was fixed on `week-2-opentelemetry` before merging (commit `5b5fa13`), and each has a test: three offline, each with a mutant, and two end to end (the sign-in and the zero samples, which only the running stack can show).

- **Grafana asks for a sign-in** (Claude). Correction to 2026-10-12: anonymous access was not off. The image's start script turns it on, with the Admin role, unless told otherwise, so anyone on this Mac could change dashboards and data sources without signing in. `compose.yaml` now sets `GF_AUTH_ANONYMOUS_ENABLED=false`. Sign in with the image's defaults, written in `compose.yaml`. An end-to-end test checks that an anonymous request gets 401. Klaxon's tools will read the Prometheus, Tempo and Loki APIs directly, which have no sign-in, so they are not affected.
- **Prometheus writes a 0 where each counter starts** (Claude). `rate()` needs two samples, and a counter's first sample already holds everything counted before its first export (every 10 s). So a burst in a run's first seconds, or a first error, never showed on the rate panels: after the lost-answer demo the dashboard was flat. The OpenTelemetry SDK sends the moment each series started counting, and Prometheus 3.14 (in the image) records a 0 there with `--enable-feature=created-timestamp-zero-ingestion`, passed through the image's `PROMETHEUS_EXTRA_ARGS`. One setting fixes our counters and the HTTP and database histograms alike. Rejected: starting our counters at 0 and exporting at once in every service (more code, and it would not fix FastAPI's and httpx's metrics).
- **Related logs searches a minute either side of the span** (Claude). Grafana's "Related logs" button (from a span to its Loki lines) searched only the span's own time, cut to whole milliseconds. It missed any line written in the span's last fraction of a millisecond, which is where a consumer logs its outcome: the confirmer's "confirmed" came 0.4 ms after the cut. `docker/grafana/datasources.yaml` is the image's data source file with `spanStartTimeShift: -1m` and `spanEndTimeShift: 1m`. The trace id filter keeps the results to the one trace.
- **`payment_id` means our id in every log line** (Claude). The consumers' outcome lines used `payment_id` for the provider's id (`pay_...`), while the payments API's lines use it for ours (`pmt_...`). A search for one payment found only half of its lines. Now the consumers log `payment_id` (ours, from the metadata) and `provider_payment_id`, and so do the confirmer's error lines (they said `klaxon_payment_id`). ## 2026-10-13 (week 2 session: the traffic generator, and the money check's cutoff)

Built on the branch `week-2-traffic-generator`, from `main`. Aravind reviews it before it is merged; nothing is pushed.

- **Known gap 3 settled: the money check works to a cutoff** (Aravind, 2026-10-13, from three options Claude laid out). The options: (1) pause the generator before each check, (2) give the check a cutoff, (3) detect traffic during a check and retry it. He chose the cutoff, Claude's recommendation. Why not a pause: only our own generator would pause, so any other client still breaks the check; Klaxon's read-only "check the money" tool (week 3) could not run during an incident without first pausing traffic, which is a write action, hides symptoms while paused, and is something no real on-call engineer can do; and a fix would only ever be verified with the traffic off. Why not retry: under steady traffic it can keep retrying and give up. The cutoff is how payment teams reconcile anyway (a closing time; later records count next time), and it keeps the check read-only.
- **"Before", measured** (Claude): `make check-under-traffic` on the check without a cutoff (commit `1300fef`, clean code; the first run on a fresh stack, the second right after it), synthetic traffic at 5 payments per second, seed 7. First run: 19 of 20 checks passed (`evidence/week2/2026-10-13T200500Z_...`). Second run, 100 checks: 81 passed, 19 failed (`evidence/week2/2026-10-13T200911Z_...`). The stack was healthy: each run's last check, on the quiet stack, passed. Every failure was the race: a payment or refund that landed between the check's reads showed as "posted, but the provider never sent it", "succeeded but never charged", or totals that disagreed. The second run failed more often because the provider's history had grown, so reading it took longer and the window was wider.
- **"After", measured** (Claude): the same command and settings on the check with the cutoff, a fresh stack each time, clean code: 100 of 100 checks passed at `8195074` (`evidence/week2/2026-10-13T210256Z_...`) and 100 of 100 at `4162abf` (`evidence/week2/2026-10-13T210628Z_...`), both quiet checks passed. In the second run, 80 of the 100 checks left records newer than their cutoff for the next check (177 provider events in all), so traffic really was in flight while they ran. Added for that reason: the measurement now records what each check left out.
- **The traffic generator runs on this Mac, not in a container** (Claude). `python -m klaxon.traffic` (`make traffic`) talks to the stack from outside, as customers do. Its output is readable in a terminal, the tests and the eval harness can run it in-process, and a change needs no image rebuild. A Compose or Kubernetes service can wrap the same module later if the eval harness needs one.
- **What the generator sends** (Claude's defaults): payments at a steady random rate (a Poisson process; 2 per second by default), amounts log-normal around $40 (between $1 and $2,000), 500 made-up customers; 2% sent twice at once, like a double click; 10% refunded 2 to 20 seconds later, in full or in half. One seeded plan: every payment takes the same draws, so the same seed and rate give the same customers, amounts, gaps and choices. Open loop: customers keep arriving when the stack slows down; past 64 requests in flight, an arrival is shed and counted.
- **How it retries** (Claude): like a careful client, with the same Idempotency-Key every time, after 0.5, 1 and 2 seconds, on no answer, a 5xx, or a 409 "still running" (honoring Retry-After). Final answers (402, 422, a refund's 409) are not retried. When the outcome stays unknown, it asks for the payment's status 5 and 60 seconds later. With the payment confirmer, a lost answer is usually settled by its webhook before the first retry, so the retry gets the confirmed payment (seen live: `pmt_000010`, 503, then 201).
- **Provider noise while the traffic runs** (Claude): `lose_ack_rate` 0.05 and `fail_after_charge_rate` 0.02 (the "lost answer"), seeded. When it stops, the generator puts the provider's behavior back as it found it, but only if nothing else changed it meanwhile, so it never undoes a fault scenario's setting. With both rates at 0 it never touches the behavior.
- **The generator only sends to this Mac** (Claude, CLAUDE.md's rule): it refuses any address but 127.0.0.1, localhost and ::1.
- **How the cutoff works** (Claude): (1) the cutoff is the second the check starts in, by the provider's clock, which stamps every record in whole seconds, as Stripe does; the check waits for that second to end (at most a second), so no new record can get a stamp up to it. (2) It settles up to the cutoff: every webhook of an event up to the cutoff acknowledged by our receiver, then where the topic ends, read once, then both consumer groups past that point. The point stays fixed, so new traffic cannot keep the check waiting. Both conditions only move one way, so seeing each once is enough (the old "quiet twice in a row" rule is gone). (3) It reads our books first, in one REPEATABLE READ snapshot fixed by a first query, then the provider's records: everything we booked from the provider is then already in its records. (4) It judges what the provider did up to the cutoff. Newer events, the postings made from them, and newer charges are reported as left for the next check. A posting the provider never sent, a payment charged twice, a payment we call succeeded with no charge at all, and one linked to a charge the provider gives to another payment are judged whatever the cutoff: no timing explains them.
- **The fake provider gains three read-only queries** (Claude): its balance as of a time (`GET /v1/balance?as_of=`, like summing Stripe's balance transactions up to a time), delivery counts for the events up to a time (`GET /admin/deliveries?created_lte=`), and its clock (`GET /admin/clock`). The last two are simulator controls, like the existing `/admin` ones: a real check would use its own synced clock and a margin of a few minutes, and could not ask the provider which webhooks it still holds. The exact clock lets the local check use "now" as the cutoff and still be exact.
- **The price of the cutoff** (Claude): a problem in a record newer than the cutoff shows one check later, seconds later. `--no-wait` keeps the cutoff and skips the settling. Known gap 4 is unchanged: a stalled consumer still makes `make check` exit 2.
- **The quiet demos print the same results** (Claude): with nothing newer than the cutoff, every summary reads as before. The first piece's two in-process demos still print exactly their saved evidence (checked 2026-10-13 after the last `src/klaxon` change).
- **Independent review** (Claude): a separate Claude review, read-only, found no false alarm under traffic on a healthy stack and agreed with the ordering argument. It found seven problems, all fixed, each with a test and a mutant:
  1. *A record the provider stamps in the future would be left for "the next check" forever,* with its problems: a clock step or a seconds-versus-milliseconds bug could hide a double posting or a wrong amount. Now the check reads the provider's clock again after reading its records. A record stamped later than that clock, or a clock that went back, makes it refuse to run (exit 2), and so does a stamp that is not whole seconds. Refusing, not failing: the money may be right, but the check cannot vouch for it.
  2. *How the cutoff flows through the check was tested only end to end,* which the mutants never run: five wiring mistakes (a different cutoff for settling and for judging, the cutoff left out of the provider read or the invariants, the cutoff chosen after settling) survived the offline tests. Offline tests now follow one cutoff through, in order.
  3. *The provider's clock was read without its store's lock.* It was safe only because the delivery count waited on that lock. Now the clock itself is read under it, and a test holds a write open.
  4. *A double click at the very end of a run* could find the thread pool shutting down and crash its payment. It is now counted as not sent.
  5. *The "this Mac only" rule could be bypassed by proxy settings:* httpx sends 127.0.0.1 requests through `HTTP_PROXY`, `ALL_PROXY` or the system's proxy unless told not to. Every client of the generator, the check, the demos and the end-to-end tests now has `trust_env=False`, and a client passed to the generator must aim at this Mac too.
  6. *Settling could overrun its deadline by one round of slow reads,* and the wait for the cutoff's second had no limit. Both are bounded now (a clock that goes back or stops is refused).
  7. *A docstring said two things are judged whatever the cutoff; the code judges four* (also a payment we call succeeded with no charge, and one linked to a charge the provider gives to another payment). Corrected.
