## 2026-10-09 (pitch-weekend session, evening)

- **First piece built to the STATUS spec, plus review fixes** (Claude; Aravind to review before the first commit). An independent Claude review found no wrong behavior but real gaps. Fixed: the dedupe row and the posting were already one transaction but no test proved it (now tested by failing the posting mid-transaction); transactions are explicit (`autocommit=True` plus `BEGIN IMMEDIATE`/`COMMIT`), so the SQLite default changing in a future Python cannot silently break atomicity or foreign keys; dedupe uses `ON CONFLICT (event_id) DO NOTHING`, so only a repeated event id counts as "seen before"; STRICT tables refuse fractional cents.
- **Ledger rows are never edited or deleted; a wrong posting is repaired by a reversal** (Claude, standard accounting practice). The money check counts a reversed posting as cancelled, so the check can pass after a proper repair. This is how Klaxon's future fix-and-verify step will repair a double posting.
- **Wording: "posted twice", not "double charge", for the first piece** (Claude, for accuracy). A duplicate webhook makes our books count a payment twice; the provider charged the customer once. A true double charge (a retried charge request without an idempotency key) is a separate fault class for later.
- **Single currency (USD).** A webhook in another currency is refused with a 400 instead of being booked as dollars.
- **Evidence is tied to the code by a SHA-256 of `src/klaxon`**, so a run is traceable even before the first commit. The demo's exit code mirrors the money check (0 pass, 1 fail).

## 2026-10-09 (week 1 session: the patient in Docker Compose)

- **Container runtime: Docker Desktop** (Aravind, over Claude's Colima recommendation). He installed it himself. Rosetta is off (`UseVirtualizationFrameworkRosetta = false` in Docker's settings): every image we use has a native arm64 build, checked with `docker manifest inspect`. Docker Desktop does not start at login (`AutoStart = false`), so open it before `make up`. Its CLI lives in `~/.docker/bin`; the Makefile and `klaxon.patient.stack` find it there.
- **Images pinned to exact tags** (Claude): `postgres:18.6-alpine`, `redis:8.8.3-alpine`, `apache/kafka:4.3.1` (KRaft, one node as broker and controller), `python:3.12.15-slim` for our services. Python libraries pinned in `requirements/services.lock.txt`, choosing releases at least about two weeks old (FastAPI 0.142.2, uvicorn 0.53.0, httpx 0.28.1, psycopg 3.3.6, psycopg-pool 3.3.3, redis-py 8.1.0, confluent-kafka 2.15.1, pydantic 2.13.5).
- **One image, four services** (Claude): fake provider, webhook receiver, payments API, ledger consumer. FastAPI with plain (sync) endpoints, because they are easier to read and explain than async ones; the Kafka client is confluent-kafka (librdkafka). Each service has a `create_app(...)` or class that tests build with fakes, and a `main()` that reads the environment.
- **The fake provider is its own service with its own books** (Claude): a SQLite file on its own volume, so a fault in our PostgreSQL can never damage the "source of truth" the money check compares against. It uses a transactional outbox and Stripe-like idempotency keys. Simulator controls (`PUT /admin/behavior`: `lose_ack_rate` with a seed, `lose_ack_event_ids`) make it lose acknowledgements on purpose, which causes real duplicate deliveries.
- **The receiver does not dedupe; it answers 200 only after Kafka acknowledges** (Claude). Dedupe happens where the money is written, in the same transaction. The dead-letter topic is `provider-events-dlq` (not `.dlq`: Kafka warns that `.` and `_` collide in its metric names).
- **The ledger consumer commits its Kafka offset only after the database commit** (Claude). Dead-letter only for problems with the message itself (unparseable, wrong currency, an amount above $999,999.99, a value the database refuses). Retry everything else forever without committing, because those are our problems and the event must not be skipped. The naive mode stays as the known-bad baseline for the money check (`LEDGER_HANDLER=naive`).
- **Redis holds the payments API's idempotency keys; PostgreSQL is the guarantee** (Claude, reading STATUS's "a database constraint plus Redis"). Redis: `SET NX` claims, saved responses for 24 hours, 409 while running, 422 for a key reused with a different request. PostgreSQL: `payments.idempotency_key UNIQUE`. The provider: our payment id as its idempotency key. When Redis is down, the API fails open to the database. Redis runs without persistence and with `noeviction`, so the database guarantee is exercised, not theoretical.
- **One database role per service, least privilege** (Claude): `ledger_writer` (SELECT and INSERT on the ledger, no UPDATE or DELETE), `payments_api` (its two tables; may update a status, never an amount), `klaxon_readonly` (SELECT everywhere, read-only transactions, 5 s statement timeout). The schema is `docker/postgres/initdb/20-schema.sql`, applied when the volume is first created.
- **The ledger's `payment_id` is the provider's payment id** (Claude), as in the first piece, so the money check compares per payment unchanged. Our own ids (`pmt_000001`) live in the payments tables.
- **The money check's SQL was made portable instead of forked** (Claude): no column aliases in HAVING (PostgreSQL refuses them) and every SUM cast to BIGINT (PostgreSQL returns NUMERIC otherwise, which arrives as Decimal). The same function now checks the SQLite ledger and the PostgreSQL ledger. `ledger.check_lines` became public so the PostgreSQL ledger reuses it.
- **"Settled" means 0 webhooks pending at the provider and ledger lag 0, twice in a row** (Claude). Only then does the live check read the ledger, in one REPEATABLE READ snapshot.
- **No circuit breaker on provider calls yet** (Claude, on purpose): timeouts and safe retries only. A provider outage is one of the planned week 2 incidents.
- **Host-side addresses use 127.0.0.1, not localhost** (Claude): `localhost` tries IPv6 first and the published ports listen on IPv4 only, which made librdkafka log connection errors.
- **Tooling** (Claude): ruff for lint and formatting of new code (line length 120, which the first piece already followed; E501 off because the formatter handles length). The first piece's files were not reformatted; one stray `f` prefix in `tests/test_signatures.py` was removed so lint passes. Starlette 1.7's test-client deprecation warning is filtered in pytest (it asks for a package named `httpx2`; not installed).
- **Week 1 lives on the branch `week-1-compose`** (Claude): Aravind merges it into `main` after his milestone review. Nothing is pushed.
- **Independent review, same evening: findings and what was done** (Claude). A separate Claude review of the week 1 code found no way to book twice, charge twice or acknowledge without a durable write in idempotent mode. Fixed: the ledger consumer crashed in a loop on a message with no value or deeply nested JSON, and retried values the database refuses forever (now the parser refuses odd input, ids must be short plain ASCII, and integrity, size and encoding errors are dead-lettered); a Redis claim could expire mid-request and its release deleted whoever held the key (now token-checked Lua scripts, a 60 s lock and a 5 s database pool timeout); logs recorded the raw request path (now the route template, strings capped at 300 characters); no Host check (now added, against DNS rebinding); a socket-only PostgreSQL health check, no recovery from a fatal Kafka producer error, no stale-connection check in the pools; five overstated docstrings; three weak tests and several missing ones, including the 409 path under real concurrency and Kafka and PostgreSQL restarts. Not fixed, recorded as known gaps in STATUS: payment status only from the provider's synchronous answer (needs Aravind's decision) and Kafka as a trusted zone (week 9 safety pass).
- **The mutation check lives in the repo** (Claude): `scripts/mutation_check.py`, `make mutants`. It works on a copy of the repo, never the repo itself. Two of its mutants first survived and exposed weak tests (a size limit hid the deep-nesting case; an unsigned request hid the Host check); both tests were fixed before the final count.
- **Evidence counts a run as clean when the code and the stack's files match the commit** (Claude): `git_clean_code_and_stack` looks at `src`, `compose.yaml`, `docker`, `requirements`, `Makefile` and `pyproject.toml`. Notes in `docs/` cannot change a run.
