### Week 3, item 2: the model adapters and the trace recorder (2026-10-15)

Built on the branch `claude/week-3-model-adapters-4aa3c1`, cut from `week-3-mcp-server` at `0c6f510` (item 1, not merged yet): `58aee11` (the adapters, the recorder, the tests and the mutants), `3885cda` (the independent review's fixes), `3cd17ec` (the mutation script runs one item's mutants with `--only`), then these docs. Not merged, not pushed: it waits for Aravind's review, after item 1's. Built in a session of its own, without Docker, while he reviewed item 1 against the stack.

- **One interface** (`src/klaxon/agent/model.py`): the loop (item 3) will call `model.ask(system, messages)` and get a `Reply`: the text, the model id the response reports, the usage, the seconds, the raw response, and where it came from. Three adapters:
  - `ScriptedModel`, for offline tests: replies from a script (a text, an error to raise, or a function of the conversation), and every call kept.
  - `ClaudeCode` (`claude_code.py`): Claude through Claude Code in headless mode (`claude -p`) on Aravind's seat, Opus 5.5 by default (`claude-opus-5-5`, his choice).
  - `ReplayModel`, for regression tests: what a live run got, given back only for the exact prompt it answered (by SHA-256), labeled as replayed. A recorded failure comes back as the same error.
- **Claude Code, set up only to answer.** It is found through `KLAXON_CLAUDE_BIN`, then the PATH, then the newest copy the desktop app keeps (2.1.295 on this Mac). Every flag is one that 2.1.295's `--help` lists: `--tools ""`, `--strict-mcp-config` with an empty server list, `--disable-slash-commands`, `--safe-mode`, `--restricted`, `--permission-mode dontAsk`, `--permission-prompts none`, `--no-session-persistence`, and `--output-format stream-json`. `make claude-command` prints the whole command. It runs in a new empty temporary folder, removed after, with an allow-listed environment: no API key, no API address, no proxy, none of a Claude Code session's variables; CLAUDE.md, auto memory, telemetry and updates off.
- **Checked as it runs.** Claude Code's first event says what it loaded. A tool, an MCP server, a memory path, another folder, a sign-in other than the seat's, or another permission mode, and Klaxon stops it at once and refuses the reply. So too a reply that ran a tool, took more than one turn, was refused a permission, or came from another model than the one asked for.
- **The prompt.** The conversation goes in on stdin, never on the command line. Each turn sits in a tag made from the conversation's own hash, so no text in a turn can end it or start one. Every at sign goes out as a fullwidth ＠, so Claude Code never reads "@path" in a log line as a file to attach (the review's top finding; whether `-p` attaches such files was not tried). Hidden characters are dropped.
- **One deadline per call** (300 s by default). At the deadline, Claude Code's whole process group is killed, and Klaxon never waits for anything else that holds its output open. After its reply, Claude Code gets 10 s to exit, then it is stopped, and the reply still counts. Its output is capped at 5 MB and parsed line by line; a line JSON cannot hold safely (NaN, deep nesting) is skipped.
- **Recording, always on.** A live adapter cannot be built without a `Recording`. Every reply is written to it before the loop sees it, and a reply that cannot be written is not returned. Every failure is written too, Klaxon's own included. Each response: the date, the model id it reports, the prompt's hash and its parts (each stored once), the text, the usage, and Claude Code's raw output with the home folder written as `~`, under the label "Recorded responses ... Not a simulation".
- **The trace recorder** (`trace.py`): one JSON line per step of a run. A start record (the goal, the model, where its replies come from, the system prompt, the tools, the budgets); a step record each (what the model saw, as hashes and sizes; its reply; what it proposed; allowed or not, and why; what ran; what came back, cleaned and capped at 8,000 characters with its full length and hash; timing and usage); a stop record (one of eight reasons, and the totals). It refuses a step that says a tool ran without being allowed, or ran something other than what was proposed. It writes the stop record itself if a run crashes, and it never overwrites a trace.
- **Commands:** `make claude-command` prints the exact command and calls nothing. `make claude-check` makes one tiny live call ("Reply with the word ok") and saves it in `evidence/week3/`. It fails if the reply is not "ok", or if the model read more than 1,500 input tokens: the check's prompt is a few sentences, so much more would mean something else reached the model.

### Week 2, item 6: refunds confirmed from webhooks, and a fifth money-check invariant (2026-10-14)

Built on the branch `week-2-refund-confirmation`, from `main` at `a433044`: `4c3c3e5` (our refund id goes to the provider and comes back in its events), `2c020f8` (refund confirmation, the fifth invariant, the traffic, the demo, the review's fixes), `ec5daa0` (the evidence), `58c7a5e` (the confirmer starts while PostgreSQL is down; found by `make e2e`), then these docs and Aravind's review runs. Known gap 1 had been set for later (Aravind, 2026-10-12); on 2026-10-14 he asked why it was deferred and chose to do it now.

- **The same fix as for payments.** The payments API sends our refund id with every refund, as metadata (`klaxon_refund_id`). The fake provider stores it and puts it, with its own refund id, in each `refund.succeeded` event; it lists its refunds (`GET /v1/refunds`); and a new simulator control (`fail_after_refund_rate`, `fail_after_refund_keys`) saves a refund, then answers 500 to every retry with its key. The payment confirmer, which used to ignore refund events, confirms a pending refund in one conditional UPDATE: only if still pending, for the same amount, not linked to another provider refund, and for the payment the provider refunded. Anything else changes nothing and is logged as an error. Its role gains column grants on `payments.refunds`: it reads five columns and may change only a status and the provider's refund id.
- **The fifth invariant** (`refunds_match_provider` in `src/klaxon/checks/money.py`): every refund of ours that the provider made is succeeded, for the same amount and the same payment, linked to that refund, and made once; every refund we call succeeded exists at the provider; the provider refunded nothing that is not ours. The cutoff's rules apply, and a refund made twice, a refund we call succeeded that the provider never made, and one linked to a refund the provider gives to another refund of ours are judged whatever the cutoff. `make check` runs all five.

## Known gaps (found in review, not fixed yet)

1. ~~Refund status never catches up.~~ **Closed 2026-10-14** (week 2, item 6, above): refunds are confirmed from their webhooks, and the fifth invariant compares them with the provider's. 3. ~~The money check assumes no client traffic while it runs.~~ **Closed 2026-10-13** (week 2, item 3, above): the check works to a cutoff. What remains: a problem in a record newer than the cutoff shows one check later.
