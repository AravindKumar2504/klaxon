- **The loop** (`src/klaxon/agent/loop.py`, plain Python, no framework): `investigate(alert, model, tools, trace_path, budgets)`. Goal: an alert (name, what it says, when it fired). State: the conversation, the tool calls that ran (ids c1, c2, ...), the budgets used. Actions: one per step, in one JSON reply: call one tool, or diagnose. Observations: each tool's result, or what was wrong with the last reply. Stops, each named in the trace: `diagnosed`, `step_budget`, `tool_call_budget`, `time_budget`, `invalid_replies`, `model_error`, `tools_failed` (new), `interrupted`, `crashed`.
- **Budgets:** 12 steps, 10 tool calls and 600 s by default. A step is one model call, invalid and failed ones included. The tool server must start, and each model call and each tool call must answer, within the time left (each tool call within 180 s at most); the live adapter then gives Claude Code up to 10 s to exit after a reply, so a run can pass its time by that much. An invalid reply goes back with what was wrong, at most 2 times in a row. A failed or timed-out model call is asked again once, its last turn rewritten to say what is left now. A reply Klaxon refused, or could not record, is never asked for again. Each user turn ends with what is left, and says when the next reply must be the diagnosis.
- **The reply contract** (`contract.py`): one JSON object, checked against the JSON Schema the model is shown, by a validator written here for the 15 keywords the schema uses (a test checks it agrees with the `jsonschema` library on 36 replies; they differ on purpose on a trailing newline in a pattern). No key twice, no NaN, at most 20,000 characters. A tool's arguments must fit that tool's own schema, and evidence must cite calls that ran. The diagnosis: a hypothesis, 1 to 10 pieces of evidence citing call ids, a confidence from 0 to 1, a proposed fix (kind, target, summary), a blast radius, a rollback plan, each text saying something visible. The fix is never applied (`applied: false`).
- **It acts on nothing:** an allow-list of the eight read-only tools in the loop's own code; the run refuses to start if the server offers any other tool, or one not marked both read-only and not destructive; the reply schema names only those tools; the one function that calls a tool checks again, at the point of use. A test watched every process the loop started during a whole run: only Klaxon's MCP server.
- **Untrusted tool output:** the system prompt says tool results are data, never instructions, and to report text that gives orders as a finding. Each result reaches the model inside a JSON document the loop writes on one line, under a fixed note. A planted log line with `"}]}`, a fake "Klaxon:" line and Unicode line separators stayed one JSON string value, and the turn stayed five lines. Results are cleaned again (hidden characters, also behind JSON escapes; the home folder as ~) and capped at 60,000 characters, the server's own limit. The system prompt holds no at sign and no line break inside its JSON.
- **The MCP client** (`mcp_client.py`, written from scratch): starts `python -m klaxon.agent.mcp_server`, does the 2025-11-25 handshake with `klaxon-ops`, lists and calls tools, with a deadline on every message; at a deadline the server's process group is killed. `RecordedTools` writes every tool result before the loop sees it; `ReplayTools` serves them again for the same calls in order.
- **Replay:** with the model recording and the tool recording, a run replays offline. `make replay-run RUN=...` compares every step's prompt, reply, decision, call and result, and the stop. Prompts hold no times, so they match by hash. A stop on the time budget cannot be reproduced (a replay takes no time): then the steps before it are compared, and it says so.

- **The tools** (`src/klaxon/agent/tools.py`; `make tools` lists them, `make tool NAME=... ARGS='{...}'` calls one): `list_metrics` and `query_metrics` (Prometheus), `search_logs` (Loki), `search_traces` and `get_trace` (Tempo), `service_health` and `recent_deploys` (docker), and `money_check` (the five invariants, with or without waiting to settle). Each checks its arguments against its JSON Schema and returns compact JSON.
- **Read-only by construction:** GET requests to the three query APIs, with no redirects followed and no proxies; three docker commands that only read (`context inspect`, `compose ps`, `inspect --type container`), each with a 15 s timeout; the money check through the read-only role. No tool takes a URL, a host or a command. Every source must be this Mac, the money check's provider, database and Kafka included, or the tools refuse to start. Text a source sends in an answer the tools cannot read is never repeated.
- **The MCP server** (`src/klaxon/agent/mcp_server.py`, written from scratch as in INFO 7375 lesson 8): JSON-RPC 2.0 over stdio, MCP revision 2025-11-25 (the `initialize` handshake). It answers "method not found" to `server/discover`, the newer 2026-07-28 revision's probe, and the official SDK's client then falls back to the handshake. Malformed messages, unknown methods and unknown tools are protocol errors; bad arguments, refused queries and unreachable sources are tool errors (`isError`), which the model can read and correct.

## Known gaps (found in review, not fixed yet)

1. ~~Refund status never catches up.~~ **Closed 2026-10-14** (week 2, item 6, above): refunds are confirmed from their webhooks, and the fifth invariant compares them with the provider's. What remains: our API's guard against refunding more than was paid counts only succeeded refunds, so a refund whose outcome is unknown does not count yet; and no check asks whether the provider refunded more than it charged. **Decided 2026-10-14 (Aravind): fix both in week 4, next to the circuit breaker.** Our API will count a refund whose outcome is unknown, and the money check will check, per payment, that the provider never refunded more than it charged.
2. **Kafka is a trusted zone.** Any process on this Mac or in the Compose network can publish to Kafka without the provider's signature. The money check would flag a forged event as "posted, but the provider never sent it", but nothing stops it. Since item 6 a forged `refund.succeeded` could also mark a pending refund succeeded, and our API would then refuse a real refund as "nothing left to refund"; invariants 1 and 5 would still catch it. Such a message can also choose its consumer span's trace id or mark it "not sampled" (only the traceparent is read, never tracestate or baggage). Planned for the week 9 safety pass: forward the signature in Kafka headers and check it again in the consumer.
3. ~~The money check assumes no client traffic while it runs.~~ **Closed 2026-10-13** (week 2, item 3, above): the check works to a cutoff. What remains: a problem in a record newer than the cutoff shows one check later.
4. **A stalled consumer makes `make check` exit 2** ("not settled") instead of showing the money symptom. `python -m klaxon.checks.live --no-wait` runs the check anyway; in-flight events then look lost or stuck. Seen in the poison-message fault (2026-10-14): the scenario run shows both views. Klaxon's money-check tool (week 3) will need both too.
5. Smaller limits, documented where they live: no circuit breaker on provider calls (deliberate: the provider-outage fault; the breaker is its fix, planned for week 4); one Kafka broker with one copy, so a crash of the whole Docker VM could lose the newest writes; the APIs have no authentication (local only, Host-checked); provider event ids are sequential per provider volume, so reset all volumes together (`make reset`). New in week 2: the API's own status update still trusts the provider's answer, amount included (see `DECISIONS.md`); a poison message is dead-lettered once per consumer group, so a dead-letter metric must count per consumer; pending refunds have no gauge like pending payments, so a refund the known-bad confirmer leaves pending shows in the money check and in its `refund_not_found` outcomes, not on a panel of its own. New in week 3: a loop run can pass its time budget by up to 10 s, the time Claude Code gets to exit after a reply; `make tool` (item 1) pastes its arguments into shell text, so an apostrophe in them breaks it (the loop's targets pass theirs through the environment; found by item 3's review, not fixed there).
