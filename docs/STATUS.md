- **The traffic generator** (`src/klaxon/traffic.py`, `make traffic`): synthetic customers on this Mac, talking to the stack from outside. Seeded payments at a steady random rate (2 per second by default), 2% double clicks, 10% refunds, retries with the same key, status checks when the outcome stays unknown, and provider noise (5% of acknowledgements lost, 2% of answers lost) that it puts back afterwards. Open loop; past 64 requests in flight, arrivals are shed. It refuses any address but this Mac, and ignores proxy settings.

Each run's quiet check passed. Every failure was the race: a payment or refund landing between the check's reads.
- **The cutoff** (`src/klaxon/checks/live.py`, `money.py`): the check takes the second it starts in, by the provider's clock, and waits for it to end; settles up to it (every webhook up to it acknowledged, then both consumer groups past a fixed point in Kafka); reads our books in one snapshot before the provider's records; and judges what the provider did up to the cutoff. Newer records are reported as left for the next check. A posting never sent, a double charge, a payment succeeded without a charge, and one linked to another payment's charge are judged whatever the cutoff. A record stamped after the provider's own clock, a clock that goes back or stops, or a stamp that is not whole seconds makes the check refuse to run (exit 2). The fake provider gained three read-only queries: its balance as of a time, delivery counts up to a time, and its clock.

So the checks passed while payments kept landing, not because none did. A check took 0.42 to 2.58 s (median 1.0 s), up to a second of it waiting for the cutoff's second to end.

## Known gaps (found in review, not fixed yet)

1. **Refund status never catches up.** Payments are fixed (week 2, above), refunds are not: a refund whose provider answer is lost stays pending, nothing confirms it, and the fourth invariant does not compare refunds. The same fix applies: our refund id as metadata, a `refund.succeeded` confirmation, refunds in the invariant. **Decided 2026-10-12 (Aravind): later.** Claude's suggested time: after the first 3 faults.
2. **Kafka is a trusted zone.** Any process on this Mac or in the Compose network can publish to Kafka without the provider's signature. The money check would flag a forged event as "posted, but the provider never sent it", but nothing stops it. Such a message can also choose its consumer span's trace id or mark it "not sampled" (only the traceparent is read, never tracestate or baggage). Planned for the week 9 safety pass: forward the signature in Kafka headers and check it again in the consumer.
3. ~~The money check assumes no client traffic while it runs.~~ **Closed 2026-10-13** (week 2, item 3, above): the check works to a cutoff. What remains: a problem in a record newer than the cutoff shows one check later.
4. **A stalled consumer makes `make check` exit 2** ("not settled") instead of showing the money symptom. `python -m klaxon.checks.live --no-wait` runs the check anyway; in-flight events then look lost or stuck. Seen in the poison-message fault (2026-10-14): the scenario run shows both views. Klaxon's money-check tool (week 3) will need both too.
5. Smaller limits, documented where they live: no circuit breaker on provider calls (deliberate: the provider-outage fault; the breaker is its fix, planned for week 4); one Kafka broker with one copy, so a crash of the whole Docker VM could lose the newest writes; the APIs have no authentication (local only, Host-checked); provider event ids are sequential per provider volume, so reset all volumes together (`make reset`). New in week 2: the API's own status update still trusts the provider's answer, amount included (see `DECISIONS.md`); a poison message is dead-lettered once per consumer group, so a dead-letter metric must count per consumer.
